# Architecture

## Shape

```
Legacy app / Explorer
        |  Win32 file I/O on \\VFS365\<user> or a drive letter
WinFsp driver (kernel, network mode)
        |
vfs365-agent.exe, one per user session, started at logon
  Drive.WinFsp   file system callbacks to engine calls
  Core           namespace, metadata cache, content cache, upload queue, change feed
  Graph          HTTP, RU governor, retries
  Agent          WAM sign-in, policy, mounts, status
        |
Microsoft Graph (delegated) to SharePoint Online and OneDrive
```

**Not a sync client**: nothing is mirrored up front. Cost scales with what users open, not with library size.

## Projects

| Project | Role |
|---|---|
| src/Vfs365.Core | Engine. Platform neutral, no front-end types |
| src/Vfs365.Graph | Thin Graph and SharePoint REST client, RU governor. Gets tokens from the host (`ITokenSource`) |
| src/Vfs365.Drive.WinFsp | WinFsp front end |
| src/Vfs365.Agent | Agent logic: settings, sign-in, commands, Explorer integration |
| src/Vfs365.Cli | `vfs365.exe`, console tool |
| src/Vfs365.Background | `vfs365-agent.exe`, no window, started at logon |
| src/Vfs365.Np | `vfs365np.dll`, network provider in C so typed `\\VFS365` paths resolve |
| installer/ | WiX 5 MSI (`installer/bundle`: setup with WinFsp); policy/ has the ADMX |
| tests/Vfs365.Tests | Unit tests |

A Cloud Files API front end, if ever built, is another `Drive.*` project over the same Core.

## Namespace

```
\\VFS365\<user>  (optionally a drive letter too)
  OneDrive\
  Shared with me\           items shared with the user (Graph search on SharedWithUsersOWSUSER): a folder is a mount rooted at its
                            path in the owner's drive (DriveMount.BasePath, no change feed), a file a read-only one-file mount
  Sites\<site>\<library>\   what discovery finds plus pinned locations, Teams and channel sites included
```

That is `Scope` = `All`, the default. With `SharePoint` the site folders are the root of the drive; with `OneDrive` the OneDrive root is. Drive letter (default none), name and filters come from policy ([DEPLOYMENT.md](DEPLOYMENT.md)).

One volume per user session. UNC prefixes are machine-wide (a second volume with the same prefix fails with `0x80070050`), so the share is the Windows user name; drive letters are per session. Each volume's security descriptor grants only its user and SYSTEM. When the prefix is taken, `DriveHost` reads the holder's owner: another user's volume (`MountConflictException.OwnedByAnotherUser`) is reported as a security problem and tried again only hourly or on Retry in the tray; it would otherwise receive saves from apps that stored `\\VFS365\<user>` paths. When the holder has the same user name in another domain (`SameNameHolder`), the message names that account instead of a generic security alert.

Typed paths: Explorer's address bar, file dialogs and Run resolve `\\server\share` through the network providers' `NPGetResourceInformation`, which WinFsp's provider lacks; file I/O on the same path works regardless. `vfs365np.dll` (`src/Vfs365.Np`) answers it for `\\VFS365` when the volume root's owner is the calling user, and declines everything else; it sits right after WinFsp's provider in the provider order. It asks for the root through WinFsp's own UNC provider (`\\?\GLOBALROOT\Device\WinFsp.Mup`, with `+<id>` from WinFsp's `SxsDir` since 2.0), never through the UNC path: a volume that isn't mounted then fails at once instead of falling through to SMB and WebDAV, which would look for a server named VFS365 on the network. 32-bit processes load the SysWOW64 copy; x64 processes on ARM64 load System32's ARM64 copy and fail, since serving both would need an ARM64X build, which Zig can't make.

- Short names for sites and libraries: Office and Explorer stop near 260 characters, SharePoint allows 400. Name cleanup as in M365AutoLink (`Marketing - Documents` becomes `Marketing`).
- Same-titled sites all get a URL suffix in brackets, the first that tells them apart: the URL's last segment, then the full path, then host plus path. Libraries use the internal name, then the list ID. Names follow the sites, not discovery order. Device names (CON, NUL, COM0 to COM9, LPT0 to LPT9) get an underscore.
- Site and library titles are cleaned up for Windows (`DriveNamespace.SafeName`); item names pass through as they are, since SharePoint already refuses the characters Windows doesn't allow.
- `~$*` lock files, `~WR*.tmp`, `desktop.ini` and `Thumbs.db` stay local and are never uploaded; other temp-like names wait (see [Write path](#write-path)).
- A navigation pane node named after `Label` (default "VFS365", HKCU delegate folder) targets the drive.

## Operation mapping

| Windows | Graph | RU |
|---|---|---|
| First listing of a folder | `GET .../children?$select=...&$top=200`, then pages of 1000 | 2 per page |
| Open a path in a folder never listed | `GET /drives/{d}/root:/{path}` | 1 |
| Read | `downloadUrl`, then ranged GETs against it; blocks cached | 1 |
| Create, write, close | PUT content up to 10 MiB, else an upload session (5 MiB fragments, smaller on slow uplinks, up to 56.25 MiB on fast ones, multiples of 320 KiB); `conflictBehavior=fail` | 2 |
| Overwrite, rename-over, `ReplaceFile` | Upload to the existing item ID with `If-Match: <eTag>` | 2 |
| Create folder | `POST .../children`, `conflictBehavior=fail` | 2 |
| Delete | `DELETE` (recycle bin, never `permanentDelete`) | 2 |
| Rename, move within a drive | `PATCH` name / parentReference | 2 |
| Move across drives | None: `STATUS_NOT_SAME_DEVICE`, so Explorer copies and deletes the files itself | - |
| Set timestamps | `PATCH` fileSystemInfo | 2 |

Error mapping (`Vfs365FileSystem.Status`): 404 to `ERROR_FILE_NOT_FOUND` / `ERROR_PATH_NOT_FOUND`, 403 to `ERROR_ACCESS_DENIED`, 409 on a folder create or move to a name collision (`ERROR_ALREADY_EXISTS`), 400 (a name or request SharePoint refuses) to `STATUS_OBJECT_NAME_INVALID`, 412 and 423 to a sharing violation where the call can still fail (a rename), else to a conflict copy.

## Start

The agent mounts with what the last run knew: libraries, their drive IDs and the OneDrive from `discovery.json`, and the folder listings the change feeds kept current from `metadata.bin` (sealed). Explorer gets the drive in about 0.1 s without a network call; discovery then runs in the background and new or removed libraries appear live. With a state under a week old (with libraries) it waits a random 5 to 90 minutes first (spreading a tenant's morning sign-ins), then searches and reads the details only of libraries checked more than a week ago (`LibraryEntry.CheckedAt`); any other start, also one after an interrupted first run, discovers at once (`DiscoverySchedule`). The first run mounts with the OneDrive and fills in the sites when discovery finishes, and saves the state at once (OneDrive-only drives too), so the next start needs no network. While the agent runs, discovery repeats about every 24 hours (plus up to 2 hours at random). A failed run, a failed or incomplete search included, keeps the last run's libraries but doesn't count as recent, sends a `discovery` monitoring row and is tried again in 15 to 60 minutes (2 to 5 minutes, doubling, while there are no libraries yet). Settings are read once at the start; a policy change is noticed within 5 minutes and logged as applying after Restart, except `MonitoringUrl` and `MonitoringDetail`, which apply then without a notification while monitoring runs. A different account at the next discovery restarts the agent cleanly with an empty cache.

A first start that can't reach Microsoft 365 (offline, sign-in not ready) waits and retries with back-off, 15 s up to 5 minutes, and at once when the network returns or the user signs in; the tray says what it waits for. Other start problems keep the tray icon with the cause, Retry and Show log, and retry hourly. A drive letter in use or not valid mounts the drive without a letter (UNC path and navigation pane) and says so.

## Agent process

- `vfs365-agent.exe` started at sign-in is a supervisor (`AgentSupervisor`): it runs the agent as a child (`--child`) and starts it again after a crash (any exit code but the agent's own 0, 1 and 2, a kill (-1), Ctrl+C and the end at logoff), at most 3 times in 15 minutes and not while the session ends. A restart from the tray starts a new supervisor; the old one ends with its child. After a crash the supervisor logs what Windows recorded (Application Error 1000 and .NET Runtime 1026, read with `wevtutil /f:xml` by event data, so any Windows language), and the new child gets `--restarted <code>` and reports it to monitoring. When the supervisor gives up it reports that itself (with the last known UPN) and shows a tray icon with Retry and Show log, unless `TrayIcon` is 0.
- `agent.log` is written through an append-only handle, one write per line, so the supervisor, the agent and an agent being replaced never overwrite each other's lines. A second agent in a session leaves the running one's log alone.
- Session end: the agent stops on `SessionEnded`, so a cancelled shutdown keeps the drive; while uploads are pending the tray sets a shutdown block reason. Restart from the tray waits, without a time limit, until the old agent has uploaded and unmounted. At unmount, local state (discovery, folder listings, statistics, a throttling episode still going on) is saved before and after the final uploads, which include files nobody closed.
- Stop signal: the event `Local\VFS365.Stop` in the user's session; only that user, SYSTEM and Administrators can create objects there. `machine-stop` (SYSTEM, session 0) reaches it as `Global\Session\<id>\VFS365.Stop` and sets it only when the user the session's agent runs as owns it, so a planted event or a symbolic link to another one is never set by SYSTEM; agents before 0.4.0 (global `VFS365.Stop.<id>`) get the same check. Its cleanup of user folders works through handles on an explicit stack, at most 64 folders deep. `machine-start` starts the agent again in every active and disconnected session after an upgrade. `machine-stop --cleanup` restores known folders for loaded profiles; an Active Setup component does it at the next logon for signed-out ones.
- Status (`StatusFile`): once the agent owns the session it writes `status.json` (state, letter, account, sign-in problem code, network, throttled, waiting and held counts, the last `error:` line, files waiting with their cause), atomically, when it changes and every 5 minutes, and "stopped" at the end; the supervisor writes "not started" while it waits for Retry. `vfs365 health` reads it (as SYSTEM through the same no-follow handles as the uninstall cleanup) with the machine checks.
- Events (`AgentEvents`): sign-in problems, security warnings, conflicts and waiting uploads, setting warnings, crashes, throttling episodes, start and stop go to the Application log under source VFS365 (`RegisterEventSourceW`/`ReportEventW`, the user's SID), only when the MSI registered the source; redacted, and rate-limited per ID.
- Drive letter check (`DriveLetterReport`): at the start and every 5 minutes, from the agent's own sign-in, it reads the letter's DOS device, `WNetGetConnection` (what Explorer asks), a remembered mapping in `HKCU\Network\<letter>` and the network provider order. Problems are logged with the fix when they change.
- Layout (`FolderRedirection`, `DriveMappings` policies): after the mount, after each discovery, hourly and after resume, one run at a time. Templates are expanded (`%UPN%`, `%UPNNAME%`, then environment variables) and resolved in the volume by `FolderTargets` (wildcards against folder names, missing folders made inside a library). Known folders move with `SHSetKnownFolderPath` (`ShellKnownFolders`); `redirection.json` records each folder's original and is flushed before each move, so a crash leaves nothing it can't put back. `MoveContents` moves item by item with `MoveFileWithProgressW` (write-through) and resumes a move left halfway. A re-run asked during a run goes once more after it (`SingleRun`). A folder counts as VFS365's to move only at its default path, its recorded original, or on the volume. At unmount every folder still where VFS365 put it goes back (not when restarting). Drive letters are DOS devices of the user's sign-in (`DefineDosDevice` to `\??\UNC\VFS365\...`, like subst), removed at unmount; `vfs365np.dll`'s `NPGetConnection` reports them as connected to their UNC path, and `MountPoints2` carries their label. A letter that a SharePoint WebDAV mapping holds or remembers is freed with `WNetCancelConnection2`.

## Explorer menu

`ExplorerVerbs.cs`, `ExplorerMenu.cs`, `VerbPipe.cs`:

- Static per-user verbs: a cascading `VFS365` entry under `HKCU\Software\Classes\*\shell` and `Directory\shell` (`SubCommands` with a nested `shell` key, `MultiSelectModel` Single), limited by `AppliesTo` (AQS `System.ItemPathDisplay:~<"<root>"` for the drive letter, `\\VFS365\<user>\` and the `DriveMappings` letters); Open in desktop app, Keep this version and Compare have an `AppliesTo` of their own (Office extensions, the copies' name pattern). Written after the mount, checked every 30 s against the letters defined, removed at a clean stop and by `machine-stop --cleanup` and the logon cleanup. Windows 11 shows them under "Show more options".
- A verb runs `vfs365-agent.exe verb <name> "%1"` (no window). It sends `name<TAB>path` to the session's agent over the pipe `VFS365.Verbs.<session>.<user SID>` (`PipeOptions.CurrentUserOnly` on both ends, 128 KiB per request, 3 s), allows the agent the foreground and ends; without an agent it shows a short message.
- The agent maps the path to the volume (`ExplorerVerbs.VolumePath`), finds the item through the engine and reads `webUrl`, `webDavUrl` and `sharepointIds` with one GET (a library's top: its root folder). Open in browser and Share open `webUrl`; Copy link puts it on the clipboard (a short STA thread); Open in desktop app opens `ms-word:ofe|u|<webDavUrl>` (Excel, PowerPoint alike), the URL percent-encoded once; Version history opens `<siteUrl>/_layouts/15/Versions.aspx?list={listId}&ID={listItemId}`. Results and problems are tray notifications (with `TrayIcon` 0 only problems, as a message). No sharing links, no permission changes.
- Conflict copies: the 412 that ends a save in a copy reads the item (as before, for the metadata-only retry); its `lastModifiedBy` (in every `$select`) and time name who saved the other version in the notification. Keep this version (`DriveEngine.KeepVersionAsync`) replaces the original with the copy like a rename-over: an upload into the original item with `If-Match`, then the copy is deleted after the settle window. It is refused when the original changed again since the copy was made (remembered for copies of this run) or since it was listed (the `If-Match`). Compare opens both, Office files in their desktop app, others in the browser; Word's comparison has no documented URL or command line, only its object model, so it isn't started.

## Tray

`Tray.cs` runs plain `Shell_NotifyIcon` on its own thread.

- Icons come from `tray\tray-{light,dark}-{normal,waiting,error}.ico` (made by `tools/New-TrayIcons.ps1`). The set follows the taskbar theme and changes with it; the size matches the system DPI.
- Show files opens the navigation pane entry (`shell:::{CLSID}`), else the drive letter or UNC path. Explorer can't parse `\\VFS365` until it has loaded the network provider.
- Restart starts the same exe with the same arguments plus `--after <pid>`. The new agent waits for the old one to exit, then mounts.
- Other items: status ("Status: up to date", or offline, throttled, waiting for sign-in; the icon's tooltip says "VFS365: up to date"), Show log, Collect diagnostics (`SupportBundle`: a zip in `%LOCALAPPDATA%\VFS365\support`, every text through `Redactor`, then Explorer with it selected; also in the supervisor's tray after it gave up), Sign in (only when a sign-in is needed), Retry (only before the drive started), Restart, Help (`HelpUrl`), and the version line, which opens the JSolve website. Every item has an access key.
- `NOTIFYICON_VERSION_4`: one Explorer window per double-click; the menu opens at the icon from the keyboard too. `WM_ENDSESSION` is handled.
- Texts are English or Dutch by the Windows display language (`UiText`); log lines and monitoring stay English.
- Notifications are grouped (`NoticeBatcher`): what arrives within 4 s is one toast per kind ("27 files are waiting to upload: offline"), with plain causes (`PlainCause`), and each kind shows at most once a minute, counting what arrived meanwhile. Policy `NotifyUploads` mutes "Uploaded".

## Front end

`src/Vfs365.Drive.WinFsp` (`Vfs365FileSystem`, `DriveHost`, `WinFspNative`):

- Operation guard: WinFsp's FINE guard (a volume-wide lock, exclusive around creates, overwrites, deletes and renames) is replaced at mount by a no-op guard (`WinFspNative.ReplaceOperationGuard`, called from `Vfs365FileSystem.Mounted` after checking the `FSP_FILE_SYSTEM` fields it relies on). On a mismatch WinFsp's guard stays and the log says why. The `winFspGuard` switch of `DriveHost.Mount` keeps it on purpose; `DriveHost.NamespaceLocked` reports it. The engine orders changes per key. WinFsp's kernel driver still holds every open and new listing while a rename runs (`FileRenameResource`), so a slow rename still stalls opens.
- Creator's sharing: without the namespace lock another open can find a new file before the creating handle's share check. The creating handle's access and share mode (from the request) are recorded on the pending file (`PendingFile.Creator`, `FsEntry.Creator`), and Open refuses conflicting opens with `STATUS_SHARING_VIOLATION` (NTFS rules) until the creator's Cleanup or Close.
- 64 dispatcher threads. Read, ReadDirectory and Write that must wait pend (`STATUS_PENDING`, then `SendReadResponse`, `SendReadDirectoryResponse` or `SendWriteResponse`): the work fills private buffers and copies into WinFsp's buffer only when answering, after a mounted check (answers after unmount are dropped). Lookups, Cleanup uploads and Rename still block a thread.
- Exact-name directory searches (`PassQueryDirectoryFileName`) are engine lookups, not scans. Cleanup is sent on every close (`PostCleanupWhenModifiedOnly` false), so empty new files upload at their close. 0-byte files read without a download. Cleanup commits only the content that handle wrote (`CommitAsync(FsEntry)`).
- Not possible: a Previous Versions tab from SharePoint's version history. WinFsp's kernel rejects `FSCTL_SRV_ENUMERATE_SNAPSHOTS`.

## Caches and transfers

- Metadata: listings per folder in memory, loaded page by page and readable while they load: the first Graph page has 200 items, the rest 1000, and the file system answers each directory query with what has arrived. A listing counts as kept current by the drive's change feed (`Maintained`) only when every folder above it is cached and lists it by ID; folders above a listed one that aren't cached are listed once in the background (one that can't be listed, a 403, is tried again after 10 minutes). Other listings are trusted for 60 s (`ListingTtl`). Maintained listings stay current without being listed again (re-listed after 24 hours as a safety net, counted from the real fetch time, also for listings restored from `metadata.bin`). They answer lookups at once within 2 minutes of the feed's last successful read (or the pushed safety interval while push is up); otherwise a lookup first waits up to 3 s for a change read, so a file opened after idle, sleep or a restart is the current version. Stale listings show at once and are refreshed in the background, reusing the known folder ID, which reports what changed; a refresh that finds the folder gone (404) drops it and what is cached below it. When Microsoft 365 can't be reached, lookups answer from the last known listing, so cached files keep opening: after a failure without an answer (no network, a timeout; `LookupDeadline` 10 s) the last known answers serve at once for 30 s, with one background retry per drive. Changes the feed applied, and local saves, deletes and renames, made while a listing loaded or refreshed are replayed onto it when it finishes. At most `MaxCachedItems` (250,000; a listing counts its items plus three) stay in memory: least recently used listings go first (a folder counts as used when one below it is), never ones loading or used in the last 2 minutes; expired lookups are pruned every 30 s. The 5th lookup under one unlisted folder within 10 s lists that folder instead. `metadata.bin` is saved only when maintained listings change (`DriveEngine.MetadataVersion` is a fingerprint of them and the delta links). Folders above a listed folder are looked up by ID and kept (`Ancestors` in the snapshot) instead of listed. Listings come sorted (`OrdinalIgnoreCase`); a big loaded listing shares one entry array between scans.
- Tree walks: a walk is 12 folder loads within 10 s that also go two levels down (a copy, search or backup; Explorer opening sibling folders for thumbnails is not one). The engine then loads the walk's next folders inside the walked subtree, depth first (children of the folder just listed, first name on top), 2 at a time, and never more than `WalkPrefetchFolders` (default 10) that the walk hasn't opened yet. The walk lists those folders anyway, so a walk that stops early wastes at most that many listings. Loading ahead stops 10 s after the walker does and pauses after throttling; the log reports per walk how many folders were loaded ahead and how many the walk used.
- Content (`StreamingContent`): downloads into a sparse cache file in 1 MiB blocks. A read waits only for its own blocks (availability is tracked per 64 KiB chunk); one ranged stream reads ahead of a sequential reader, starting at 1 block and doubling to 8 each time a reader follows it, a read elsewhere gets its own stream (at most 3; the one idle longest makes room), idle streams stop. Every stream asks for the listed version (`contentTag`); another version (also a download whose ETag names one) or another length (`ContentChangedException`) fails the read once instead of mixing versions, the listing takes the item as served, and the next open reads it whole. A stream that gets no bytes for 90 s (read in 64 KiB pieces) is a failed attempt, and a read waiting on a stalled stream stops it. A download that failed 3 times is dropped, so the next open starts fresh; handles still holding it retry after 10 s. The length served comes from the cache file, also after a restart; a download of an item deleted meanwhile is not kept. A download read ahead in the background is promoted to foreground priority when a user reads it. `downloadUrl`s come with a `$select`ed item GET and are reused per item version for 20 s, in memory only.
- Copies out of the drive (`DriveEngine.ReadAhead.cs`): when 3 files of a drive start being read within 10 s, the next small files (up to 4 MB) of the folder being read are downloaded ahead in listing order, 4 at a time, and never more than `ReadAheadFiles` (default 8) that weren't opened yet. Measured: 300 small files copied out of a cold drive in 21 s instead of 115 s, with the same requests and every file downloaded ahead used.
- Cache: `cache\<drive>\<item>-<version>`, AES-256-GCM in 64 KiB chunks with a per-user key wrapped by DPAPI (`cache.key`): a random nonce per file, each chunk authenticated with the file's drive, item version, length and chunk number, so any range reads on its own and a damaged or altered file (`CacheDamagedException`) is dropped and downloaded again. Layout: content, then the 16-byte tags, then a 24-byte footer. The key marker includes the format, so an older cache is emptied once. Least recently used files go above `CacheSizeMB` (sizes tracked per file); older versions go when a newer one lands. Wiped on `vfs365 signout`, another account or tenant, and Intune unenrollment; a library that disappears from discovery and items the feed reports deleted lose their content. Staging files (unsaved changes) are plain and transient. The index of cached files is in memory; a released download is kept 45 s (thumbnailer, property handler and player share it); trimming runs in the background, not on the reader's path.
- Uploads: a file over 4 MiB whose size is set before it is written (Windows' copy engine does) uploads in 5 MiB fragments while it is written; each write waits while the previous fragment is in flight, so copy progress follows the network and the close sends only the last fragment. Rewriting bytes already sent, or a streaming upload that fails, falls back to a whole upload on close.
- Upload sessions of a whole file (`DriveApi`): fragments start at 5 MiB, halve (down to 320 KiB) after one that took over 30 s and double (up to 56.25 MiB) after four fast ones; timing uses the monotonic clock and fragment bodies stream from the file. A failed fragment is retried from the range the session expects next (the HTTP client doesn't resend fragments); an expired session starts over once. Before the last fragment the item is checked again: a content change fails the upload, a metadata change doesn't.
- Journal: a record next to each staging file with unsaved changes, with a `Flushed` marker set at each close (the staging file forced to disk; a file's first journal, not flushed yet, isn't forced); the next start re-uploads them into the original item (If-Match, so a server change since then gives a conflict copy).

## Change feed

`DriveEngine.Changes.cs`:

- A drive gets a feed on real use (a subfolder, a deeper path, a file open, a write, a second look at its top 10 s or more later), not when Explorer only glances at a library's top: `GET /drives/{id}/root/delta?token=latest` returns a delta link for "from now on" without listing anything; the baseline time is taken when it answers.
- Reading it returns changed items with their parent's ID; they are applied to cached listings by item ID (adds, edits, deletes, moves), through an item ID index per listing. Each change is also checked against the folder IDs of cached listings: a folder deleted, renamed or moved elsewhere drops its cached subtree even when its parent isn't cached, and two listings claiming one folder ID are both dropped. Echoes of the engine's own uploads change nothing, and an older eTag from a stale read never replaces a newer one. A failed catch-up continues from the page that failed. After a long time away (last read over an hour old) a catch-up still running doesn't make old listings current. An expired link (410) drops the drive's cache and starts over; a catch-up longer than 10 pages for a drive with fewer cached listings than that starts over too. Every listing page and change read is given up after 3 minutes without an answer (`CallTimeout`).
- Wake-ups: a socket.io push channel per drive used in the last 10 minutes (`GET .../root/subscriptions/socketIo`, Engine.IO 3 over a WebSocket; a notification carries no details, so it triggers a delta read, 3 s plus up to 10 s at random after it, joining further notifications, and at least 30 s apart per drive). A notification within `ChangeCheckSeconds` (20 s) of the last read waits until that long after it, so both are one read. Without push: on use every 15 s and in the background every 60 s while active. With push: a safety read every 15 minutes, and a catch-up read 0 to 30 s at random after the channel comes up, skipped after a read less than 30 s before. A notification is read at once only while the drive is hot (used within 2 minutes); otherwise the feed is marked behind, the next use reads first, and a drive still in use is read within 5 minutes. No feed reads while background requests are paused after throttling.
- Push channels (`DriveNotifications`): connecting times out after 60 s; a channel with no traffic for the server's ping interval plus ping timeout is reconnected. Reconnects back off from 5 s to 5 minutes plus 0 to 100% at random, starting over only after a channel stayed up 60 s. No channel while the drive's feed fails.
- Hot libraries: a drive used in the last 2 minutes is also read every `ChangeCheckSeconds` (default 20 s), so a change shows within about 20 s even when SharePoint's push is slow. With push up, every read doubles the interval (20, 40, 80, 160 s) and only a local write resets it; without push, each read that brings no change doubles it up to 80 s and a change resets it. Opens within 3 s after the engine reported changes (Explorer reading them again) don't count as use. Paused while background work is paused after throttling.
- Failed reads back off per drive from 1 to 30 minutes, give or take 25% at random (pushes and hot checks wait too); when the network returns or the PC resumes, failed feeds are read again within 30 s. The log says what went wrong once per problem and again when reads work. Meanwhile listings are read again when opened (`ListingTtl`). A `403` with `serviceReadOnly` ("Database Is Read Only": SharePoint maintenance or a site move) is `RemoteError.ReadOnly`: writes into such a library wait and retry, and failed uploads and deletes back off from 30 s to 15 minutes.
- A change below a folder doesn't report the folder as modified (only a new name or time does).
- Changes reach Windows through WinFsp's `Notify` (Explorer refreshes, `ReadDirectoryChangesW` watchers see them); a batch `NotifyBegin` refuses is tried up to 5 times. Paths are sent upper-cased, matching the names WinFsp keeps when no normalized name is returned.
- Push latency is SharePoint's: 7 to 31 s measured from a change elsewhere to the notification, usually about 25 s, often two notifications per change.

## Discovery

M365AutoLink's user-version method, proven in production:

1. `GET /me/drive` gives the OneDrive URL; dropping `-my` from its host gives the tenant's SharePoint root.
2. SharePoint Search, security-trimmed to the user: `GET <root>/_api/search/query?querytext='contentclass:STS_List_DocumentLibrary -Path:"https://<tenant>-my.sharepoint.com*"'&sortlist='docid:ascending'&trimduplicates=false&rowlimit=500&selectproperties='...'&Properties='EnableMultiGeoSearch:true'&ClientType='VFS365'`, paged in a stable order with `IndexDocId>` the last DocId until a page has fewer than 500 rows. Each page's DocIds must rise, not repeat and come from one geo; otherwise, or when a page has no DocId, search pages by row number (`DiscoveryResult.SearchNote` says so). Colleagues' OneDrives (`*/personal/*`, always excluded, also when policy sets its own `ExcludedSites`) are left out; multi-geo tenants get every geo. SharePoint-audience token.
3. Per site: include/exclude URL wildcards and site templates (policy), then `<web>/_api/site` for `WriteLocked` / `ReadOnly`; a 403 there (access to a library but not the site) counts as read/write.
4. Per site, when 2 or more of its libraries need reading: `<web>/_api/web/lists?$filter=BaseType eq 1` answers all of them at once (and refreshes the others for free); a library missing from that answer, or a 403/404 on the web, falls back to `<web>/_api/lists/GetById('<listId>')`, retried on the site collection URL on 404. Skipped: `Hidden`, `BaseTemplate` other than 101, `IsCatalog`, `IsSystemList`, system libraries by internal name (`EntityTypeName`: `SiteAssets`, `Style Library`, `FormServerTemplates` and so on, the same in every site language), M365AutoLink's template feature IDs, `ExcludeFromOfflineClient` (admin opted the library out of offline clients). Never by title: titles are localized. `ForceCheckout` libraries show read-only.
5. Library key `siteId|webId|listId`. The Graph drive is resolved lazily on first open (`/sites/{host},{siteId},{webId}/lists/{listId}/drive`) and cached.

Differences from M365AutoLink: no item-count limits (nothing is synced), and removal means hiding the folder. A library is hidden only when 2 runs in a row didn't find it (`DiscoveryState.Misses`, `DiscoveryReconciler`), so one incomplete search answer doesn't wipe its cached files. When a search page fails, nothing is hidden and no misses count (the run fails, see [Start](#start)). The deletion circuit breaker stays: when the result shrinks by more than 40% against the last run, misses still count, and the shrink is accepted after 3 runs in a row. Libraries hidden by policy (site URL patterns and site templates) or now excluded by the library rules don't count: they go at once, whatever their share. Access is enforced by SharePoint anyway, so a stale folder only costs a 403. The last run's state is matched by tenant ID, so a user moved to another geo keeps it.

Cost: site and library metadata are cached on the device and reused for a week per library (`MetadataMaxAge`), so a routine run is the search pages plus lookups for new libraries and those checked more than a week ago (measured: 1 search call, 1.4 s; a full refresh is about 90 calls). A library read for the first time gets a check time up to 24 hours back (fixed per library), and a run re-reads at most half the sites (at least 10) with expired metadata, oldest first, so the re-checks spread over several days. Exclusions are cached the same way (`DiscoveryState.Exclusions`) and re-checked with the metadata, so a hidden library shown again appears within a week. Pinned URLs that resolve to nothing are remembered for the metadata age (`EmptyPins`). SharePoint publishes no RU cost for REST search. `vfs365 discover --audit` checks recall against site search, followed sites and hubs.

Not found by search: sites excluded from search, Restricted Content Discovery sites, sites newer than the index, the root site (outside the default include patterns), and other tenants (guests can't search the host tenant).

Each run's skipped libraries (with the reason), errors and libraries it hid because runs in a row missed them go to `discovery-report.json` (`DiscoveryReport`; hidden ones stay listed 30 days). The drive never reads it; `vfs365 why` explains a link or name from it, `discovery.json` and the policy (`LocationExplainer`), and `--check` asks SharePoint whether the user can open the location and whether search returns it.

Pinned locations cover these within the tenant (other tenants are out of scope): URLs from policy `PinnedLocations` and `vfs365 pin <url>` (`%LOCALAPPDATA%\VFS365\pinned.json`).

- The web is the longest path prefix that answers `_api/web`, never above `/sites/x`. Non-JSON answers count as "not a web": SharePoint returns a page for paths below a page.
- A site URL adds its document libraries; a library, folder or view URL adds the list `GetList` finds at the longest prefix.
- Site templates come with each search hit (`SiteTemplate`, the site collection's; no configuration number), so template rules cost no calls.
- Pinned libraries pass the library rules but not the site patterns or templates, show under their site, reuse metadata for a week and keep their last result when a lookup fails.

## Throttling

Per app per tenant, shared by every VFS365 user in that tenant (values in `src/Vfs365.Graph/ResourceUnits.cs`):

| Licenses | RU per minute | RU per 24 h |
|---|---|---|
| up to 1,000 | 1,250 | 1,200,000 |
| 1,001 to 5,000 | 2,500 | 2,400,000 |
| 5,001 to 15,000 | 3,750 | 3,600,000 |
| 15,001 to 50,000 | 5,000 | 4,800,000 |
| over 50,000 | 6,250 | 6,000,000 |

Per user: 3,000 requests per 5 minutes, shared with the user's other apps. On 429 or 503 every request pauses and `Retry-After` is honoured, clamped to 1 s to 5 minutes, plus 0 to 50% at random; when the pause ends, waiting requests go one by one (foreground 100 ms apart, background 500 ms), so a tenant's devices don't all come back at once. Reads are retried on 500, 502 and 504 with jittered back-off; writes (PUT, POST, PATCH, DELETE) only on 429 or 503 with `Retry-After`, since a write that failed with a 5xx may have happened (a retry would give a false conflict). `RateLimit-Remaining` at or below 20% of `RateLimit-Limit` holds background requests until `RateLimit-Reset`, and `x-ms-resource-unit` replaces the estimate, when SharePoint sends them. User-Agent `ISV|JSolve|VFS365/<version>`. JSON batches of up to 20, each sub-request priced on its own.

Handler (`M365Client.CreateHandler`): the system proxy with the user's default credentials, 15 s connect timeout, connection lifetime 5 minutes, idle 2 minutes, no automatic decompression (JSON requests ask for gzip themselves; downloads never do). Pauses, the budget's refill, release slots and download URL reuse run on a monotonic clock (`MonotonicClock`), so a wall clock set back holds nothing. A GET that failed on the way is sent once more after 1 s. `ThrottledWithin` tells the status and tray whether a throttle ended recently.

Timeouts: the agent's `HttpClient` has none overall. `M365Client` fails a request whose response headers don't arrive within 100 s (counted from the last byte sent) or that makes no progress for 60 s in either direction, so a slow upload or download that keeps moving completes.

Own budget (`RequestBudget`): every request is priced by method and URL (`ResourceUnits.Estimate`: listings and SharePoint REST 2, item and delta reads 1, writes 2, pre-authenticated transfer URLs 0) and taken from a per-user token bucket of `ApiBudgetPerMinute` units (default 600) that holds one minute's worth. Work marked background (`RequestPriority`: change feed, lookahead, refreshes, discovery, push setup) only takes from the upper half, so a request a user waits for gets units first; work a user joins (a download read ahead, then opened) is promoted through its `PriorityHolder`. After a 429 or 503 every background request waits `ThrottlePauseMinutes` (default 15; 1 to 1.5 times that, at random) in the client; foreground requests only wait for `Retry-After`. Resource units in the statistics count every attempt sent, as Microsoft counts them.

Tokens go only over https on the default port to Microsoft Graph and the tenant's own SharePoint hosts (`TrustedHosts`: root, `-my` and multi-geo locations); any other URL, for example from a pin, is refused before a token is requested.

## Monitoring

`Monitoring.cs`: with policy `MonitoringUrl` (a table service SAS URL) the agent adds entities to the customer's tables over the Table REST API (`POST /<table>?<sas>`, JSON, `Prefer: return-no-content`): `errors` at once (rate-limited), `statistics` per day from counters kept in `statistics.json` (`UsageStatistics`, fed every minute from `M365Client.Usage`; resource units also per UTC hour, and the busiest fold as the day's peak minute; the dashboard's Headroom tab sets them against the tenant's per-app limit), and `devices` from the installer (`vfs365.exe machine-report` as SYSTEM). Fire and forget on a separate `HttpClient` with a 15 s timeout. Error rows are not retried; a day's statistics stay in `statistics.json` until a send succeeds (tried again an hour later, for up to a week after the first failed send). Each day keeps the device it was used on (the file roams with pooled AVD profiles) and a random RowKey suffix, so a re-send still conflicts and nobody can add the row first. The first failure is logged once. The SAS is never logged, only the account. `MonitoringTarget.Parse` refuses a SAS that can read, list, update or delete rows or reaches other services (it needs `ss=t`, `srt` with `o`, and `sp` with `a` and at most `c`), since every user on the PC can read the policy; the log, `vfs365 settings` and `machine-report` say why. `MonitoringDetail=NoPaths` replaces file and folder paths in error rows with `[path <hash>]` and keeps only the host of URLs. Throttled responses are grouped into episodes (`ThrottleEpisodes`: until 2 minutes without one after the last pause ended), logged and sent as one `throttled` row each, with the numbers as columns; `HeldSeconds` is the pause Microsoft asked for, not the longer `ThrottlePauseMinutes` background work waits. Sources include `security` (another user's volume holds this user's UNC path, or the name VFS365 resolves to an address other than 0.0.0.0 or loopback) and the supervisor's own "not started again" crash row, which carries the last known UPN.

## Identity

Windows' Web Account Manager, called directly through its WinRT interfaces (`Wam.cs`, `WamTokenSource.cs`; no sign-in library or broker runtime is shipped), as a multi-tenant public client, JSolve's app unless policy names the customer's own: silent SSO with the Windows account, CAE (`cp1`): a 401 with an `insufficient_claims` challenge is retried once with the claims. Two audiences: Graph for files, SharePoint for discovery.

WAM silent calls time out after 30 s. One request is in flight per resource, and failures are cached with a back-off (1 to 15 minutes), so a Conditional Access block isn't asked again on every request. Cached tokens are returned without a lock; silent sign-in takes one lock per audience. The background agent never opens a sign-in window by itself while it runs: a request that needs one fails at once (and for 30 s without trying again), sets `SignInProblem` with plain words, and the tray offers Sign in. A window opens only from the tray's Sign in, a click on the notification, or a first start without saved state; with `TrayIcon` = 0, which has no Sign in, a needed sign-in opens it by itself, once per problem. Never while a lock is held, one at a time; after a cancel, nothing opens by itself for 15 minutes. `vfs365 whoami --sign-in` shows the window even when the Windows account would do, to test the prompt. The account and tenant are logged at the first token and on a change.

Only member accounts in their own tenant: a token whose account's home tenant differs from the token's tenant (a guest, or an account synced in from another tenant) is refused.

Tenant: forced by policy or config, else the device's Entra join or registration, else `organizations` and the sign-in decides. Nothing tenant-specific is configured by default; the SharePoint host comes from the OneDrive URL. Delegated scopes only ([APP-REGISTRATION.md](APP-REGISTRATION.md)); tenants on default consent settings need admin consent (MC1097272). WAM needs an interactive session, so the agent runs per user, not as a service.

## Data safety rules

- Acknowledge a write only when it is durably queued.
- Delete server content only on an explicit user delete, never because a local file is missing or an I/O call failed.
- Upload saves to the existing item ID with `If-Match`. A mismatch gives a conflict copy, never an overwrite. Conflict names carry the time to the second and a counter when taken.
- Flush before acknowledging: staging files are flushed before a deferred or background close returns, the journal is forced to disk before it is renamed into place, and an application's flush reaches the disk (`FlushFileBuffers`).
- Only the volume's user and SYSTEM get in: the volume's security descriptor grants only them, and before any lookup the file system checks the requester's token (from WinFsp's request) and refuses others, so another user on the host can't probe names or spend the user's budget. It also runs `AccessCheck` with that token against the volume's descriptor: the user's app container and restricted tokens (sandboxed renderers) are refused, low integrity tokens may read. If the token can't be read the check fails open and WinFsp's own descriptor check decides. The network provider only vouches for `\\VFS365\<user>` when the volume root's owner is the caller.
- Multi-user database files (`.accdb`, `.mdb`, `.qbw`, SQLite) can be read-only or blocked by policy `DatabaseFiles`, also as rename targets: byte-range locks don't cross machines. Default `Allow`.

## Write path

Write-through, built in `DriveEngine.Writes.cs`. Application save patterns reach SharePoint as one new version of the same item:

- A file being changed gets a local staging copy (from the content cache). Reads and writes go to it.
- When the handle that wrote closes, the upload runs before the close returns (WinFsp's request timeout is raised to its maximum, 10 minutes, for slow lines). A close can't report an error, so a 412 or 423 there ends in a conflict copy next to the file. A 412 caused by a metadata-only change (same cTag) is retried once with the current eTag instead.
- New files (`BackgroundUploads`, on by default) are the exception: they are journaled when created, so their close returns at once and they upload right after, 4 at a time. Copying 300 small files to the drive: 3 s instead of 171 s, all uploaded after 29 s.
- A file closed again within `RepeatSaveSeconds` (default 30) of its last upload uploads once, at the end of that time: an app that opens, appends and closes a log uploads it once per window instead of on every append.
- The write gate orders changes to local state and is held only for bookkeeping: journal writes and flushes run after it is let go (`ReleaseGate`), and adopting an upload into the cache happens after it (`AdoptLater`: a hard link of the staging file is encrypted into the cache, reads use the staging file meanwhile). Every transfer lets it go (uploads, the download that stages a file for writing, rename uploads and replaces), so other files go on; operations on the affected paths wait for it. A file written to while it uploaded uploads again; each staged file has a reader/writer lock so a write in progress always ends before its upload is judged unchanged.
- Handles follow their content (`DriveEngine.Follow`): through renames, into the item a save became (new files too), and into the conflict copy after a conflict. Reads follow this engine's save only for handles on the version it replaced; a colleague's newer version is served as is, and a write through a handle on an older version ends in a conflict copy. Writes to a file deleted or replaced meanwhile fail with `STATUS_FILE_INVALID`.
- A failed upload never ends unscheduled: it retries with back-off (sign-in problems included) and notifies once. A 404 or 410 on the existing item (deleted in Microsoft 365 while edited) uploads the file anew under its name, or as a conflict copy when the name is taken; a rename-save into such an item creates it anew too. A 400 (a name or request SharePoint refuses) is permanent: the file stays local, is notified once and is listed as "Not saved" in the log when the drive stops, until it is saved or renamed again.
- A delete Microsoft 365 refuses (locked, or no permission to delete) shows the file again and notifies with the reason; one refused item never holds up other work.
- After a crash, a journaled file is compared with the server item before it is uploaded again; the journal is rewritten whenever its base, path or flush state changes. Changes that were never flushed (written, not closed) upload only as a `<name> (recovered <time>)` copy, never into the item; journals from before 0.5.0 count as flushed.
- Folders the drive creates are known to be empty, so files created in them need no lookups.
- A rename of a staged file onto a real name is the commit point of Office-style saves: the content goes into the item that owns the destination, and a 412 or 423 fails the rename, so the application reports it. This upload stays inside the rename on purpose (decision 42 in `private/DECISIONS.md`); a download's final rename and folder renames return at once.
- Deletes, and renames of a file to a temp name, stay local for a 10 s settle window. A save that lands on that path in the meantime goes into the original item (Word renames the original away, Excel deletes it). Unclaimed renames are undone; deletes are applied per item in the background, with a shared limit of 4, without holding up saves, and are promoted to the foreground when an operation waits on one; a folder delete drops the separate deletes of files below it. Folder DELETE and PATCH run as transfers. A deferred DELETE carries `If-Match`: on a 412 a content change keeps the file (shown again, `NotDeleted` notice), a metadata-only change deletes with the current eTag.
- A file with changes not uploaded yet that is renamed to a temp name is tracked as a renamed-away original too, so a Word save can't delete it. A claimed original renamed to a real name (Word's backup copy) becomes a copy of the version before the save, or the rename is refused when that version isn't cached; the saved item never moves.
- Folder renames and moves carry files still waiting to upload along. New files are addressed by their folder's item ID (`UploadTarget.ParentId`), so a folder rename doesn't wait for uploads below it. A new file renamed to a free name while it uploads moves at once and its item follows (`FollowNameAsync`).
- Writers are counted per pending file: only the last close commits, with a 10-minute safety net that uploads anyway.
- Create and rename refuse with `NameCollision` when local state holds the name. An unclaimed alias renamed onto an existing item replaces that item's content.
- A lost answer to an upload is checked by quickXorHash (`QuickXorHash.cs`) before anything is resent; when the item can't be looked up, `UploadUnconfirmedException` stops a blind resend. Crash recovery compares by hash too.
- Never uploaded as new files (`LocalOnlyNames`): `~$*` lock files, `~WR*.tmp`, `desktop.ini`, `Thumbs.db`. Other temp-like new files (a leading `~`, `.tmp`, Excel's 8 hex digits) are journaled and upload when still there 5 minutes after their close. Content of a server item, and a rename onto a name that exists on the server, are never held back this way.
- Moves between libraries return "not same device": Explorer then copies and deletes itself.
- Memory-mapped writes arrive as paging I/O, often with no close after them: the file uploads 3 s after the last one.
- Not yet: client timestamps are not sent, a user renaming a file to `.tmp` sees it revert.
